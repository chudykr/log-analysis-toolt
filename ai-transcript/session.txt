     Each story file uses the same template:

     - Story: "As a … I want … so that …"
     - Description: detailed context, examples taken from the sample logs, edge

     - Acceptance criteria: testable, Given/When/Then where it helps

       and the tests that go with it
     - Dependencies, Estimate (S/M/L), Out of scope

     Design decisions the stories are built on

     Recorded in development-plan/README.md so every story points to one place.

     Topic: Usage
     Decision: python -m loganalyzer webserver.log auth.log, no required
       flags
     Why: "Super simple to use"
     ────────────────────────────────────────
     Topic: Runtime
     Decision: Python 3.11+, standard library only
     Why: Nothing to install to run it
     ────────────────────────────────────────
     Topic: Format detection
     Decision: Each line is tried against the known parsers; no --format
       flag
     Why: One command for any mix of files
     ────────────────────────────────────────
     Topic: Rules
     Decision: rules.toml shipped as default, --rules my.toml to override
       (tomllib)
     Why: Configurable, allows comments, no regex escaping pain
     ────────────────────────────────────────
     Topic: Rule types
     Decision: pattern (regex on one event field) and threshold (N matching
       events per source IP inside a time window, optional escalation when a
       success follows)
     Why: Two types cover every case in the samples
     ────────────────────────────────────────
     Topic: Volume
     Decision: Line-by-line generators, per-IP sliding windows in deques,
       memory does not grow with file size
     Why: "High volumes continuously"
     ────────────────────────────────────────
     Topic: Bad input
     Decision: Malformed lines are counted and listed in the report, never
       fatal
     Why: The sample contains one
     ────────────────────────────────────────
     Topic: Output
     Decision: Human text by default, --json for machines, grouped by source
       IP, sorted by severity
     Why: Clear and actionable
     ────────────────────────────────────────
     Topic: Exit codes
     Decision: 0 no findings, 1 findings, 2 usage or input error
     Why: Usable in CI and cron
     ────────────────────────────────────────
     Topic: Tests
     Decision: pytest (the only dev dependency), unit tests per module plus
       one e2e on the sample logs
     Why: Basic coverage as requested

     ────────────────────────────────────────
     ID: US-05
     Story: Detect suspicious activity
     Main tasks: Detection engine for both rule types; default rules listed
       below; severity levels
     ────────────────────────────────────────
     ID: US-06

     Story: Understand and submit the tool

       future work such as follow mode); AI conversation transcript in the
       repo

     The e2e test also checks exit code 1, that --json output parses and
     contains the same incidents, and that plain IPs such as 192.168.1.10 are
     absent from the findings.

     Known limitations to state in the plan

     - auth.log timestamps carry no year or timezone; the tool assumes --year
       (default current year) and UTC. Correlation is therefore by source IP,
       not by exact time alignment.
     - Continuous follow mode (tail -f style) is out of scope; the streaming
       design leaves room for it and it is listed as future work.

⏺ The production requirement asks for three things: handle high volume, run
  continuously, and cope with an evolving environment. We already cover high
  volume and an evolving environment fairly well. Running continuously is the
  real gap.

  Already in the code

  Need: High volume
  How it's handled: Files are read one line at a time, never loaded whole
  Where: parsers.read_lines
  ────────────────────────────────────────
  Need:
  How it's handled: Each line is read once; each rule only sees the event
    kinds it cares about; regexes are compiled once when rules load
  Where: detector.Detector.__init__
  ────────────────────────────────────────
  Need:
  How it's handled: Memory has caps: time windows only keep events inside the
    window, idle per-IP state is cleared every 10k events, each finding keeps
    at most 20 evidence lines, and at most 100 malformed lines are stored
  Where: detector._expire, _sweep, models.MAX_*
  ────────────────────────────────────────
  Need: Evolving environment
  How it's handled: Rules live in a TOML file, so tuning or adding a rule
    needs no code change; a bad rules file is rejected with all its errors at
    once
  Where: rules.toml, rules.load_rules
  ────────────────────────────────────────
  Need:
  How it's handled: A new log format is one parser function added to a list
  Where: parsers.PARSERS
  ────────────────────────────────────────
  Need:
  How it's handled: Unexpected input doesn't stop the run: malformed lines are
    counted, and unknown sshd messages are kept as auth_other
  Where: parse_stream, parse_auth
  ────────────────────────────────────────
  Need: Automation
  How it's handled: Exit codes 0/1/2 and --json output, so it fits cron, CI
    and log pipelines
  Where: cli.py

  What's missing

  1. Continuous mode. The tool reads files to the end, prints a report and
     exits; it can't follow a log that keeps growing. The detector is already
     incremental (Detector.feed() takes one event at a time), so the fix is
     mostly in the CLI:
     - --follow to keep reading new lines, handling log rotation, plus - to read
       from stdin, e.g. tail -F … | loganalyzer -.
     - Print each finding as soon as it fires or escalates, one JSON object per
       line, so a SIEM or alerting tool can consume it live.
  2. Memory in long-running mode. The finding list and the dict of pattern-rule
     findings grow with every new attacker. That's fine for one batch run but
     not for a process running for days. Finished findings need to be printed
     and then dropped.
  3. Ordering across files. Each file is assumed to be in time order. In a live
     stream, lines from several sources arrive interleaved, so they should be
     merged by timestamp (heapq.merge), allowing a few seconds of out-of-order
     lines.
  4. Spotting a changed log format. If the server's log format changes, every
     line becomes "malformed" and detection goes quiet without any error. A
     warning when the malformed rate crosses a threshold (say 5%) turns that
     into a visible problem. This is cheap to add and very relevant to an
     evolving environment.
  5. Compressed rotated logs. Rotated logs are usually .gz. Supporting them is
     one gzip.open call in read_lines.
  6. Proof of the volume claims. The volume smoke test planned in US-08 (200k
     lines, under 10 s, under 150 MB) isn't written yet. Until it exists,
     "handles high volume" is a claim, not something we've tested.
  7. Year rollover in syslog. auth.log lines have no year, so a log that runs
     across New Year will get the wrong year after midnight. In follow mode the
     year can come from the current date instead.

  Beyond a single machine, the honest answer is that this tool is the detection
  step, not the whole pipeline. At real scale it would sit behind a log shipper
  such as Vector or Fluent Bit, be split by source IP across several instances,
  and send its JSON output into a SIEM. That belongs in the README, not in code.

  Recommendation

  Add a new US-10 "Continuous and production mode" covering 1, 2, 4 and 5, and
  finish item 6 as part of US-08. Leave cross-file merging, the year rollover
  and multi-machine scaling as "known limitations / future work" in the README.
  That keeps the tool simple for a reviewer: one command still just works, and
  --follow is opt-in. It also gives a tested answer to every word in the
  production requirement.

  What US-10 covers:
  1. More input sources: stdin (-), and gzip files recognised by their content,
     so rotated logs like auth.log.1 and auth.log.2.gz both work.
  2. --follow mode: works like tail -F, polling every 0.5 s. A line written in
     two chunks is joined before parsing. It handles both kinds of log rotation
     (rename-and-recreate, and truncation). Ctrl+C or SIGTERM stops it cleanly,
     prints a summary and exits with the usual code.
  3. Findings as they happen: the detector reports each finding when it opens,
     escalates or closes. In follow mode that prints one text line per change,
     or one JSON object per line with --json.
  4. Flat memory in a long run: closed findings are printed and then dropped.
     Idle state is also cleared every 30 s, not only every 10,000 events. At
     most 100,000 sources are tracked at once; when that cap is hit, the least
     recently seen is dropped.
  5. Warning when the log format changes: if more than 5% of a file's last 1,000
     lines can't be parsed, the tool warns once on stderr. The sample files
     stay below that, at 3%.
  6. Measured, not claimed: a test feeds 1,000,000 events and checks that memory
     stays flat.
